# 取り扱いマニュアル — 長編小説執筆リポジトリ

このファイルは、本パッケージを受け取った Claude Code と利用者の双方に向けた運用マニュアルである。Claude は、このディレクトリで最初のセッションを開始したとき、`CLAUDE.md` に続けて本ファイルを読み、ここに書かれた順序と役割分担に従って作業する。

規約が競合した場合の優先順位は次のとおり。

1. 利用者の明示的な指示
2. `CLAUDE.md`（最優先のリポジトリ規約）
3. `guidelines/` の該当ファイル
4. 起動中のスキルの `SKILL.md`
5. 本マニュアル

---

## 1. このリポジトリは何か

三人称多元視点の日本語長編Web小説を、数十万字を超えても**設定・時系列・人物像・伏線・情報格差を破綻させずに**書き上げるための執筆環境である。

中心にある考え方は3つ。

1. **書く前に固定する** — 世界観、人物、視点、プロットを執筆前に確定し、本文から推測し直さない。
2. **正本を分離する** — 「誰が何を知っているか」「今どこで何を持っているか」を台帳ファイルで管理し、本文を読み返して再構築しない。
3. **書いた後に機械検査する** — 記号事故と定型化を検出スクリプトで潰し、文章のリズムと具体性は文脈判断で直す。

1リポジトリ＝1作品で運用する。複数作品を書く場合は、パッケージを作品ごとに展開する。

## 2. 最初の1回だけ行うセットアップ

### 2-1. 環境を確認する

| 必要なもの | 用途 |
|---|---|
| Claude Code | 執筆・診断・スキル実行 |
| bash | `scripts/*.sh` |
| Python 3.11以降 | `scripts/*.py` |
| GNU grep | `scripts/check.sh` のPCRE検査 |

```bash
bash --version
python3 --version
echo "あ" | grep -P 'あ'
```

最後のコマンドが `あ` を出力しなければ、`scripts/check.sh` は動作しない。macOS標準の grep は `-P`（PCRE）に対応していないため、GNU grep を導入するか、WSL または Linux で検査する。**検査できない状態を「合格」として扱ってはならない。**

### 2-2. 実行権限を付ける

```bash
chmod +x scripts/*.sh
```

### 2-3. 作業ディレクトリを生成する

```bash
bash scripts/init-work.sh
```

`work/` と `world-bible/` の骨組みを、`templates/` を元に生成する。**既存ファイルは上書きしない**ので、再実行しても安全である。

### 2-4. 導入を検証する

```bash
python3 scripts/audit-repo.py
```

`FAIL 0` なら導入完了。1件でも FAIL があれば、その内容を利用者へ報告し、原因を解消するまで執筆を始めない。

| 本文 | `work/drafts/episode<NNN>.txt` |

## 4. 執筆を始める前に凍結する設計

新作では、次の順に `templates/` を元に作品資料を作り、**執筆前に凍結**する。凍結後の変更は各ファイルの改訂ログに記録する。

1. **`world-bible/`** — 世界法則、地理、勢力、暦、技術水準。`00-INDEX.md` に「どの話でどれを読むか」を書く。
2. **`work/character-sheet-<名前>.md`** — 視点人物と主要人物。台詞の一人称・二人称・呼称・語尾・禁則語、視点フィルタ（何に注目し、何を比喩の源にするか）まで埋める。
3. **`work/pov-plan.md`** — 場面ごとの視点割当と、事実ごとの情報格差マトリクス。三人称多元視点の中枢。
4. **`work/plot.md`** — アーク、伏線台帳、キャラアーク、作品基本情報（目安字数、場面転換記号）。
5. **`work/scene-cards/ep<NNN>.md`** — 1話単位の設計。書く直前に作る。
6. **`work/style-samples.md`** — この作品の声。第3話まで書けた時点で、**実際に書けた本文から抜き出して**埋める。長編で最初に崩れるのは規則違反ではなく声の漂流であり、それを止められるのは規約ではなく実例だけである。

資料が不足したまま本文を書き始めない。軽微な不足は既存資料から保守的に補い、補完内容を状態差分へ記録する。**人物の根幹、世界法則、主要筋を変える判断だけは、本文を確定する前に利用者へ確認する。**

## 5. 1話を書く標準手順

利用者が「第12話を書いて」と依頼した場合、Claude は次のように動く。

### Step 0. 入口を決める

新規本文の依頼は必ず `long-novel-orchestrator` を入口にする。複数話でも1話ずつ完了させ、前の話が完了するまで次へ進まない。

### Step 1. 必要な資料だけを順に読む

巨大な資料を無差別に全文読み込みしない。次の順で、今回必要な範囲だけ読む。

1. `work/continuity/current-state.md` — 直前話の終了状態
2. `work/scene-cards/ep<NNN>.md` — 今回の局所目標
3. `work/pov-plan.md` — 該当話の視点割当と情報格差
4. 登場する人物の `work/character-sheet-*.md`
5. `work/style-samples.md` の基調と、その視点人物のサンプル
6. `work/plot.md` の現在アークと前後3話
7. `world-bible/00-INDEX.md` が指定する必要な正典
8. 前話ドラフト末尾の1場面

全文を読むのは、総合診断、設定変更、重大な矛盾が疑われる場合だけとする。**アーク境界では逆に絞らない。** 話をまたいで蓄積したずれ（人物像の漂流、呼称の揺れ、伏線の散逸）は小分けに読むと見えないため、総量が収まる限り全話を一度に読んで横断照合する。

### Step 1.5. 制約を逐語引用で確定する

本文を書く前に、今回の執筆を縛る事実を資料から**逐語で引用**した制約ブロックを作る。要約や記憶で代替しない。資料を読んだつもりで書き始めることが、人物像・情報格差・時系列が破綻する最大の原因である。

引用するのは、登場人物の位置と所持品、視点人物が知らない事実、話す人物の一人称と語尾、scene-cardのmust_use_factsとNG語、直前話の作中日時に限る。制約ブロックは `work/continuity/episodes/ep<NNN>.md` の冒頭へ残す。

引用した内容とscene-cardの指定が食い違う場合は、本文を書かずに矛盾を報告する。

### Step 2. 本文を書く

`narrative-style-web-novel` の文体モード（地の文主体／会話主体／混合）で執筆し、`work/drafts/episode<NNN>.txt` へ**小説本文だけ**をプレーンテキストで保存する。設計の説明や見出しを本文ファイルへ書かない。

守る規則の要点は次のとおり（詳細は `guidelines/`）。

- 1場面1視点。視点変更は場面境界だけで行い、切替後3文以内に視点人物と知覚アンカーを示す。
- 視点人物が知らない事実、他人の内面を地の文へ書かない。
- 地の文で人物の固有名を書くときは、視点人物を含む全員を敬称・役職名なしの呼び捨てにする。台詞と明示的な内心の呼称はキャラシートに従う。
- 抽象説明より、具体物、五感、身体反応、人物固有の判断を優先する。
- 各場面で最低1つ、開始時と終了時の状態を変える。
- 前話の語彙・比喩・構文を無意識に再利用しない。

### Step 3. 検証する

`validate-episode` の修正モードで、機械検出、視点・キャラ・情報格差・時系列の照合、`ai-novel-detector` による診断、必要箇所の `humanize-ai-writing` 改稿、再検証まで通す。

### Step 4. 台帳を更新する

確定した本文だけを根拠に、次を更新する。予定や解釈を正典化しない。

- `world-bible/log/canon-log.md`（追記のみ）
- `world-bible/core/08-timeline.md`
- `work/pov-plan.md` の情報格差
- `work/continuity/episodes/ep<NNN>.md`
- `work/continuity/current-state.md`

更新後に台帳の整合を機械照合する。`[NG]` が残っている状態で完了と報告しない。

```bash
python3 scripts/state_check.py --strict
```

## 6. 完了の定義

本文を書いただけでは完了ではない。次をすべて満たしたときだけ「完成」と報告する。

- [ ] 設計資料と正典を読み、今回の制約を逐語引用で確定した
- [ ] 本文を `work/drafts/episode<NNN>.txt` へ保存した
- [ ] `bash scripts/check.sh --strict` の違反がゼロになった
- [ ] 視点・キャラ・情報格差・時系列を資料と照合した
- [ ] `ai-novel-detector` で診断し、必要な改稿を `humanize-ai-writing` で行い、再診断した
- [ ] 話単位の状態差分と正典台帳を更新した
- [ ] 改稿後に機械検査と `python3 scripts/state_check.py --strict` を再実行した

1つでも欠ける場合は、未完了としてどの段階が残っているかを報告する。

## 7. スキルの一覧と使い分け

| スキル | 役割 | 起動条件 |
|---|---|---|
| `long-novel-orchestrator` | 新規執筆の最上位入口。話をまたぐ順序と整合性を管理 | 新しい話を書く依頼で必ず使う |
| `write-episode` | 1話を設計確認から台帳更新まで完遂する内部ワークフロー | 通常は orchestrator から呼ばれる |
| `validate-episode` | 既存本文の検査・改稿 | 検査／修正の依頼、write-episode からの呼出し |
| `narrative-style-web-novel` | 本文の文体レイヤー（3モード） | write-episode / validate-episode の中で使う |
| `ai-novel-detector` | クリシェクラスタ走査と28観点診断 | 検証段階、または診断依頼 |
| `humanize-ai-writing` | 診断票を受けた本文の接地改稿 | 改稿段階 |
| `novel-plot-advisor` | 企画・プロット・読者への約束の相談 | 利用者が明示的に相談を求めたときだけ |
| `novel-worldbuilding-advisor` | 世界観・文化・旅程・通貨などの相談 | 利用者が明示的に相談を求めたときだけ |

**相談専用スキル2つは、執筆ワークフローから自動的に呼ばない。** また、利用者が指定していない作品ファイルを勝手に読み書きしない。

### スラッシュコマンド

| コマンド | 内容 |
|---|---|
| `/write-episode 12` | 第12話を執筆から検証・台帳更新まで完遂する（`12-15` で連続話） |
| `/validate-episode 12` | 既存本文を検査する |
| `/plot-advisor <相談内容>` | 企画・プロットを壁打ちする |
| `/worldbuilding-advisor <相談内容>` | 世界観を壁打ちする |

自然文（「第12話を書いて」）でも同じワークフローが起動する。

## 8. 検証コマンドと結果の読み方

```bash
bash scripts/check.sh --strict work/drafts/episode012.txt
python3 scripts/normalize_blanklines.py --check work/drafts/episode012.txt
bash scripts/chars.sh work/drafts/episode012.txt
python3 scripts/state_check.py --strict
```

`check.sh` は本文そのものを、`state_check.py` は台帳の側を検査する。長編で先に壊れるのは台帳のほうで、本文ファイルと状態差分ファイルの対応、作中日時の連続、現在状態との一致、日付の正本（`world-bible/core/08-timeline.md §3`）と状態差分の突合、伏線の設置と回収、情報格差の事実IDを照合する。

**意味的な照合はスクリプトの対象外である。** 本文の出来事と状態差分の対応、canon-log の確定事項との整合、人物ごとの位置・所持品・負傷の連続は、本文の散文を読んで判断する必要があるため、`validate-episode` と `guidelines/06-revision-checklist.md` の目視手順が受け持つ。`state_check.py` が `[NG]` ゼロでも、これらが照合済みになるわけではない。

どちらも出力は2段階に分かれる。**この区別を混同しない。**

- **`[NG]`** — 機械的に一意な規約違反（マークダウン痕跡、他言語混入、閉じカギ前の句点、記号の派閥揺れなど）。`--strict` で exit 1 になる。**必ず直す。**
- **`[警告]`** — 統計指標（過去形の連続、頻出語、説明動詞の多用など）。exit code に影響しない。本文を読み、作品意図と人物の声に照らして採否を決める。**正当な表現を消すために日本語を歪めない。**

補助コマンド：

```bash
bash scripts/check.sh --help                       # セクション名一覧
bash scripts/check.sh --section lang <ファイル>     # 他言語混入だけ検査
python3 scripts/audit-repo.py                      # リポジトリ構成の一括監査
python3 scripts/cliche_check.py <ファイル>          # 直訳クリシェのクラスタ検査＋リズム参考値
```

最後のコマンドは直訳クリシェ・感情ぼかしのクラスタ警告（話単位上限・近接密集・場面末尾）と、文長CV・同一文末連続などのリズム参考値を返す。警告は採否判断の対象で、接地改稿するか `work/continuity/cliche-allowlist.txt` へ理由つきで登録して解消する（`guidelines/05-ai-guardrails.md §3-4` が正本）。リズム参考値は合否条件ではない。閾値を決めて数値を目標にすると、場面の速度と無関係な文長調整が始まり、かえって平坦になる。

`normalize_blanklines.py` は空行の過剰を検出する。自動整形は、Webからの貼り付けなどで空行が肥大した本文に対して、利用者の許可がある場合だけ適用する。

## 9. やってはいけないこと

- 検査が実行できない環境で「合格」と報告する。
- `[警告]` を消すために自然な日本語を不自然に書き換える。
- AIらしさを消す目的で誤字や不自然な崩しを作る。人間らしさは、具体性、偏り、含意、人物固有の判断から作る。
- 台帳に「物語が進んだ」のような抽象要約を書く。記録するのは、追加された事実、変化した関係、負傷・所持品・位置、未回収の約束、新たに知った人物である。
- 追記専用（append-only）の台帳の途中行を黙って書き換える。
- 利用者の既存の記述を、確認なしに上書きする。
- 場面の途中で視点を移す。他人の内面を断定する。
- 固定の台詞比率、比喩の数、文数を品質基準にする。

## 10. トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| `grep -P` でエラーになる | GNU grep でない。WSL／Linux を使うか GNU grep を導入する。検査不能を合格にしない |
| `check.sh` が全項目OKで終わる（違反があるのに） | ロケールが UTF-8 でない可能性。`python3 scripts/audit-repo.py` で自己診断する |
| スキルが起動しない | そのディレクトリで新しいセッションを開始する。`.claude/skills/<名前>/SKILL.md` の存在を確認する |
| `work/` が無い | `bash scripts/init-work.sh` を実行する |
| 話数と資料の対応が分からない | `work/continuity/current-state.md` の「最終確定話」を見る |
| 文字数が目安と合わない | `bash scripts/chars.sh` の実数と `work/plot.md` の目安を比較する。字数のために内容を薄めない |
| 設定が矛盾している疑いがある | アーク境界の監査を前倒しし、`canon-log` と `08-timeline` を突き合わせる。矛盾の解消を次話の執筆より優先する |

## 11. 用語

| 用語 | 意味 |
|---|---|
| 正典（canon） | `world-bible/` に固定した、作品世界の確定事実 |
| 台帳 | 状態や確定事項を記録するファイル群（canon-log、continuity、pov-plan） |
| 情報格差 | 誰がどの事実をいつ知ったかの差。視点人物が知らない事実は地の文へ出さない |
| 視点アンカー | 場面冒頭で視点人物を確定させる、その人物固有の知覚描写 |
| 引き | 話末に置く、次を読む理由（問い、危険、関係変化、報酬の予感） |
| 場面転換記号 | 場面の区切りに使う記号。作品ごとに `work/plot.md` で1種類に固定する |
