# 04. プロット構造・章立て・あらすじ・タイトル

物語構造のテンプレ化と「読後感の薄さ」「水増し」「あらすじの淡々さ」を回避するための構成規約。

---

## 0. 設計の6層階層（長編・50万字超で必須）

短編・中編は「転換点 → 本文」で済むこともあるが、**長編（100話超・50万字超）では6層を分離して管理する**。これがないと、伏線が散逸し、副筋が止まり、各話が「整える章」になりやすい。

```
[層1] 規約       CLAUDE.md＋guidelines/          全作品不変
[層2] 世界観     world-bible/core/        1作品不変
[層3] 転換点     beat-sheet.md                   採用した構造の転換点（任意の参考資料）
[層4] プロット   plot.md                         中粒度（フリーズ）
[層5] シーン     scene-cards/ep<N>.md            1話単位（毎話差分）
[層6] 本文       （Claude Codeの出力）
```

| 層 | ファイル | 読み込み方 | 性質 |
|---|---|---|---|
| プロット | [`templates/plot.md`](../templates/plot.md) | 現在アークと前後3話だけ読む | アーク／主筋副筋／キャラアーク／伏線台帳／感情曲線。作品ごとに凍結する |
| シーンカード | [`templates/scene-card.md`](../templates/scene-card.md) | 当該話のカードを毎話読む | 1話単位の目的／葛藤／状態差分／話末効果／確定事実／開示禁止情報 |

### 各層の役割

- **層3 転換点**：採用した構造の主要転換点。必要な作品だけ作り、以降は参考資料として参照する
- **層4 プロット**：ビートを章クラスター（部・アーク）に展開。**主筋・副筋・キャラアーク・伏線を並列管理**。書き始める前にフリーズし、章を跨いで一貫性を保つ
- **層5 シーンカード**：1話を書く**直前**に埋める。「いま書く章で読者に渡すもの」を明文化し、伏線の設置／回収・開示禁止情報を当該話単位で固定

### 50万字超で起こる典型破綻と本階層での対策

| 破綻 | 対策する層 | 仕組み |
|---|---|---|
| 伏線が回収されないまま完結 | 層4 プロットの **§伏線台帳** | 設置時に回収章を予約し、執筆中に常時参照 |
| 副筋（Bストーリー）が止まる | 層4 プロットの **§プロットライン** | A/B/C の現在地と、次に動かす条件を追跡 |
| キャラの内的変化が描かれない | 層4 プロットの **§キャラアーク表** | 起点→中継1→中継2→終点を予約 |
| 各話が「整える章」になる | 層5 シーンカードの **§3 シーンゴール／§5 状態差分** | 「読者に渡すもの」を1〜3行で明文化 |
| 既出キャラの髪色・口調がブレる | 層2 世界観 + character-sheet | 当該場面の登場人物だけ執筆前に固定参照 |
| 開示してはいけない設定を先に出す | 層5 シーンカードの **§9 開示禁止情報** | 当該話単位で核心をロック |
| 章を跨いで時系列・経過日数が破綻 | 層2 世界観の **core/08-timeline.md** | 暦・史実・章別作中日付を一元管理（日付の正本）。scene-card §1 へ転記し、章完成後に1行追記 |

### Claude Codeの段階読み込みとの対応

- 層1は `CLAUDE.md` と、当該作業に必要なガイドラインを読む
- 層2は `world-bible/00-INDEX.md` から必要な正典だけを選ぶ
- 層3〜4は現在アークと前後3話に絞る。アーク境界や重大矛盾の疑いがある場合のみ全文監査する
- 層5は当該話のシーンカードを必ず読み、本文確定後も一次資料として保存する

## 1. プロット構造の選択

### 1-1. 基本フレーム

| 構造 | 適性 | 用途 |
|---|---|---|
| 三幕構成（25/50/25）| 万能。映画・小説共通の標準 | 長編・中編 |
| Save the Cat 15ビート | 三幕構成の細目盛 | 章単位の機能設計 |
| 起承転結 | ログライン・短編向け | あらすじ構築 |
| 序破急 | キャラアーク向け | 主人公の変化を描く |

構造は作品の読者への約束とジャンルに合わせて選ぶ。`templates/beat-sheet.md` のSave the Cat 15ビートは診断用の候補であり、すべての作品へ強制しない。

### 1-2. Save the Cat 15ビート（採用時の参考）

| # | ビート | 機能 | 配分 |
|---|---|---|---|
| 1 | Opening Image | 主人公の現状を象徴する場面 | 1% |
| 2 | Theme Stated | 物語のテーマを誰かが台詞で漏らす | 5% |
| 3 | Set-Up | 日常・キャラ紹介・伏線設置 | 1〜10% |
| 4 | Catalyst | 事件発生・主人公の世界が崩れる | 10% |
| 5 | Debate | 主人公が決断を迷う | 10〜20% |
| 6 | Break into 2 | 主人公が新世界に踏み出す | 20% |
| 7 | B Story | サブプロット・恋愛・友情線の開始 | 22% |
| 8 | Fun and Games | 約束された見せ場 | 20〜50% |
| 9 | Midpoint | 上昇／下降の転換点 | 50% |
| 10 | Bad Guys Close In | 敵の包囲・主人公の追い詰められ | 50〜75% |
| 11 | All Is Lost | 最大の喪失・どん底 | 75% |
| 12 | Dark Night of the Soul | 主人公が絶望する内省場面 | 75〜80% |
| 13 | Break into 3 | 解決の糸口を見つける | 80% |
| 14 | Finale | クライマックス・全要素回収 | 80〜99% |
| 15 | Final Image | 冒頭と対の場面で変化を示す | 99% |

この構造を採用した作品だけ、シーンカードへ「現在のビート名・達成すべき機能」を転記する。他の構造では作品側の転換点名を使う。

### 1-3. Web小説特有の調整

- 作品ページと序盤で約束した読み味を、読者が判断できる早さで具体的な場面として示す
- 報酬駆動型では早めに小さな返済を置く。ミステリー、ホラー、文芸、没入型では謎、恐怖、関係、語りの魅力を約束にできる
- 話末は次話を読む理由を残すが、毎回危機や疑問形にせず、達成、余韻、決断、意味の反転も使う

## 2. 章立てと話数

### 2-1. 1話の長さ
- **作品ごとの正本は `work/plot.md` §作品基本情報の「1話の目安字数」**とする
- 投稿先、ジャンル、更新頻度、場面の切れ目、読者の端末を考慮して目安と許容幅を決める
- 字数から場面を水増しせず、一話の状態変化と読み終わりの単位が成立する位置で切る
- 目安から外れた話は自動失格にせず、分割・統合した方が読者の理解と期待に効くかを確認する

### 2-2. 完結話数

完結話数は、読者への約束、主要因果、キャラアーク、未回収事項が閉じる位置で決める。丸い数字も端数も品質や生成手段の証拠ではない。字数や話数を不自然に調整すること自体を避ける。

### 2-3. 章末の引き

話末では、その話で変わった状態を読者が受け取り、次に残る圧力が分かるようにする。問い、危機、選択、達成、余韻、関係のずれ、既知情報の意味反転などから、場面の必然に合うものを選ぶ。同じ型が続く場合だけ変化を検討する。

## 3. あらすじ作成

### 3-1. 診断に使う4要素

あらすじの入口が弱いときは、以下のどこが欠けているか確認する。全要素を同じ比重で詰め込まない。
1. **フック**（読者が「読みたい」と思う仕掛け：意外性・対比・謎）
2. **キャラ**（主人公が誰で、どんな立場か）
3. **葛藤**（主人公が何に立ち向かうか・何を失うか）
4. **期待値**（読者がこの物語に何を期待できるか）

### 3-2. 機能不足を起こしやすいテンプレ

| ダメ | 理由 |
|---|---|
| 「これは○○が△△する物語」だけで終える | 立場・変化・期待が具体化されにくい |
| 「これは──の物語」 | 同上 |
| 体言止めの羅列 | リズム単調 |
| 出来事をただ列挙 | フック不在 |
| 大仰な前置き＋淡々本編 | 温度差 |

### 3-3. 例

Before（テンプレ）：
> 「これは婚約破棄された侯爵令嬢が、辺境の王弟殿下に拾われ、新しい人生を歩む物語」

After（4要素入り）：
> 『あなたとの婚約は破棄する』──十年支えた婚約者の言葉に、私は静かに頷いた。誰も知らないけれど、彼の借金を肩代わりしていたのは私だ。返済記録の束を抱えて辺境へ向かう私を待っていたのは、王宮を追われた変人扱いの王弟殿下と、崩壊寸前の領地経営。さあ、ここから本当の人生を始めよう。

### 3-4. あらすじ自己チェック（観点24対応）

あらすじ作成後・新作公開前に、媒体と作品に関係する項目を確認する：

- [ ] 読者が主人公の立場、変化、対立、期待できる読み味を必要な範囲で判断できる
- [ ] 定型文や体言止めの反復が、新しい情報を運ばずリズムだけを作っていない
- [ ] **物語の冒頭1〜2話に登場する具体的な事件・場面**が含まれている（抽象的な要約のみではない）
- [ ] 「壮大なあらすじ＋淡々本編」の温度差が無い（あらすじのテンションを本文1話の冒頭が引き継げている）
- [ ] 半角スペース・三点リーダ派閥揺れ・ダッシュ派閥揺れが無い
- [ ] あらすじ末尾が、作品の読み味と次に知りたいことを損なっていない
- [ ] 句読点「、」を1文の中央に過剰に打っていない（「Aは、Bだ。」型）
- [ ] 生成支援を使った場合も、回数を目的にせず、**4要素と本文との整合が満たされるまで**必要な箇所を改稿する

### 3-5. あらすじ依頼の入力項目

Claude Codeへ依頼する場合は、固定プロンプトを複製せず、次の情報を渡す。

```
投稿先と表示上限：
想定読者：
主人公の立場と欲求：
最初の不可逆な変化：
中心対立と失うもの：
読者へ約束する体験：
本文序盤で実際に起こる具体的な場面：
避ける誤読・明かさない核心：

本文との期待を一致させ、説明の重複を削る。出力はあらすじ本文のみ。
```

## 4. タイトル作成

### 4-1. タイトルの役割と現況確認

以下は入口で読み味を伝える構造例であり、現在の主流を固定するものではない。投稿先と対象ジャンルの現況を助言する場合は、最新ランキングを時点付きで確認する：
- 「[主人公属性]、[意外性]だが、[結果]だった件」
- 「[失敗・追放]、しかし[逆転]」
- 「[弱者]の[強み]で[勝利]」

### 4-2. 構成要素

タイトル候補では、一覧で伝える必要がある要素を選ぶ：
- 主人公属性（職業・身分・年齢）
- 意外性・転（「実は」「だが」「しかし」）
- 結果・テーマ（「〜することになった」「〜だった件」）
- 感情フック（「〜だが、もう遅い」）

### 4-3. 点検候補

- 抽象だけのタイトルは、検索入口や読み味が伝わらない場合がある。文芸性や既存読者への訴求が機能するなら一律に排除しない
- 派閥揺れ：タイトル内で `——` `――` `—` 混在
- 半角スペース：タイトル内に半角スペース混入

## 5. テンプレ展開の回避

### 5-1. なろう典型テンプレ（要警戒）

「ワンオペ経理令嬢→評価されず追放→新しい場所で同じ仕事→ヒーローと結婚→裁判で勝つ→元相手没落」骨格。

### 5-2. 独自要素の注入

テンプレを完全否定する必要はない。表面に特技や奇抜な小道具を足すのではなく、主人公の選択、代償、関係、成功条件のどれかを作品の核から変える：
- 主人公が経理だけでなく**料理が異常に得意**
- 元の家の没落に**主人公が最後の温情**でヒントを与える（だが受け入れられず本当に没落）
- スパダリヒーローに**過去の失敗エピソード**を1つ
- 裁判ではなく**料理対決**でケリをつける
- 「数字／帳簿は嘘をつかない」を**使わずに勝つ**

### 5-3. クライマックスの選択肢を増やす

テンプレ化すると「裁判で勝つ」「審判で勝つ」へ収束しやすい。代替：
- 暴露（証拠の物理提示）
- 第三者の証言
- 主人公の自発的撤退（負けを選ぶ）
- 共闘
- 取引・赦し

## 6. 「水増し」の回避

### 6-1. 水増しの典型症状

- 同じ言い回しがしつこく繰り返される
- あらすじに書いた事件が最初の数話で終わり、その後何十話も停滞
- 別キャラ・別視点で全く同じシーンを再描写
- 退場したキャラがしれっと復活
- 更新は速いが進行は遅い

### 6-2. 各章の進捗チェック

各章で開始時と終了時の状態を変える。変化は次の分類で記録できる：
- 情報開示（読者が知らなかった事実が判明）
- 関係変化（キャラ間の関係が変わる）
- 場所移動（物理的に進む）
- 決断（主人公が選択する）
- 喪失または獲得（何かを失う／得る）

達成できていない章は削除または統合する。
